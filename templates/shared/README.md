# Native Shopify storefront apps

A SwiftUI iOS app (`ios/`, iOS 17+) and a Jetpack Compose Android app (`android/`, minSdk 26) for one Shopify store, generated by Argon. Both read the Storefront API (`2026-10`) and check out with Shopify's Checkout Kit.

## Run

- **iOS** (on a Mac): open `ios/App.xcodeproj` in Xcode 16+, pick a simulator, press Run.
- **iOS without a Mac**: see [below](#ios-without-a-mac-xtool).
- **Android**: open `android/` in Android Studio and press Run, or `cd android && ./gradlew assembleDebug`.

### iOS without a Mac (xtool)

[xtool](https://xtool.sh) builds the app on Linux or Windows (through WSL) and installs it on an iPhone over USB. `ios/Package.swift` and `ios/xtool.yml` are there for it; they build the same sources as the Xcode project.

1. Install xtool and its prerequisites, following its [installation guide](https://xtool.sh/documentation/xtool/installation-linux): Swift, `usbmuxd`, the `Xcode.xip` download for the iOS SDK, and `xtool setup` to sign in with an Apple ID.
2. Connect the iPhone by USB, trust the computer, and turn on Developer Mode (Settings → Privacy & Security).
3. Run `cd ios && xtool dev`.

xtool has no build settings, so the app reads its per-store values from `ios/Config.xcconfig`, which `xtool.yml` copies into the app. `xtool.yml` also lists every file the app reads from its bundle (the GraphQL documents, the home banners): when you add one, add it there too. With a free Apple ID the installed app expires after 7 days and xtool prefixes the bundle ID.

## Configuration

One key list, two files with the same key names. Edit, then rebuild.

| Key | Meaning |
|---|---|
| `SHOP_DOMAIN` | The store's `*.myshopify.com` domain, no `https://` |
| `STOREFRONT_TOKEN` | Public Storefront API token from the Headless channel |
| `CUSTOMER_CLIENT_ID` | Customer Account API client ID (client type Public (mobile app)). Empty hides login |
| `SHOP_ID` | Numeric shop ID; the login callback is `shop.<SHOP_ID>.app://callback` |
| `API_VERSION` | Storefront API version, `2026-10` |
| `APP_NAME` | Display name under the app icon |
| `BUNDLE_ID` | iOS bundle ID / Android `applicationId` |
| `PDP_METAFIELDS` | Product metafields to list on the product page, comma-separated `namespace.key` (e.g. `custom.material,custom.care`). Empty shows none |
| `HOME_TEMPLATE` | Home screen layout: `fashion`, `beauty`, `grocery` or `b2b` |
| `COLLECTION_TEMPLATE` | Collection layout: `top` (sticky sort and filter bar) or `bottom` (floating bar) |
| `JUDGEME_PUBLIC_TOKEN` | Judge.me *public* API token, for product reviews. Empty still shows them, with less detail |
| `SHOW_VENDOR` | `true` shows the vendor on product cards and the product page. `false` (the default) hides it, as Shopify's own themes do |
| `ONBOARDING` | `true` (the default) shows a three-page welcome the first time the app opens. `false` skips it |
| `FREE_SHIPPING_THRESHOLD` | The cart total from which shipping is free, as a number in the shop's currency (e.g. `150`). The cart shows the progress towards it. Empty hides the bar |
| `META_APP_ID`, `META_CLIENT_TOKEN` | The Meta app's ID and client token, for [analytics](#analytics). Both empty leaves Meta out |
| `MOENGAGE_WORKSPACE_ID`, `MOENGAGE_DATA_CENTER` | The MoEngage workspace ID and its data center, `1` to `6`. An empty workspace ID leaves MoEngage out |
| `SERVER_PURCHASE` | Who reports the purchase to Google Analytics: the app (`false`, the default) or `server/` (`true`). Read [Purchases from a server](#purchases-from-a-server-server) before turning it on |

- iOS: `ios/Config.xcconfig` (`KEY = value`)
- Android: `android/shopify.properties` (`KEY=value`)

With an empty `STOREFRONT_TOKEN` on any store other than `mock.shop`, the app shows a setup screen naming the missing key.

## App icon and launch screen

Argon made both from the store's logo (Shopify admin → Settings → Brand) when it generated this project. They are part of the app, so nothing changes them at run time. To change them, replace these files and rebuild, or set the logo in Shopify and generate the project again.

| File | Content |
|---|---|
| `android/app/src/main/res/drawable-xxxhdpi/launcher_logo.png` | The logo in the Android icon and on its launch screen: at most 264×264 px, transparent background |
| `android/app/src/main/res/values/launcher.xml` | `launcher_background`: the colour behind that logo |
| `ios/App/Assets.xcassets/AppIcon.appiconset/AppIcon.png` | The iOS icon: 1024×1024 px, no transparency |
| `ios/App/Assets.xcassets/LaunchLogo.imageset/LaunchLogo.png` | The logo on the iOS launch screen: at most 600×600 px, transparent background |
| `ios/App/Assets.xcassets/LaunchBackground.colorset/Contents.json` | The iOS launch screen's background colour |

The colour is the logo's own background where it has one, else white.

If the store had no logo Argon could use, Android has its default mark instead of the first file (a vector, `res/drawable/launcher_logo.xml`; delete it when you add `launcher_logo.png`, because a resource can't be both), and iOS has a plain icon and an empty launch logo. With xtool the icon is the same `AppIcon.png` (`iconPath` in `ios/xtool.yml`) and the launch screen stays plain.

## Page templates

Both apps carry every template; `HOME_TEMPLATE` and `COLLECTION_TEMPLATE` pick the ones shown. Change the value in both config files and rebuild.

- **Home**: `fashion` (editorial, image-led), `beauty` (soft cards, ratings, shop by routine), `grocery` (search first, dense rows, quick add), `b2b` (SKUs, trade prices, bulk quantities). Each lays out the store's banners, collections and product rows from [the home screen content](#edit-the-home-screen).
- **Stock banners**: until the store has its own banners, each template shows three photos from Shopify's Burst library (`android/app/src/main/assets/home/`, `ios/App/Resources/home/`). Delete the ones of templates you don't use.
- **Collection**: `top` keeps sort and filter chips in a sticky bar under the title; `bottom` puts Sort and Filter in a floating bar. Colour filters and product cards show swatches: Shopify's swatch data where the store has it, else a colour matched from the name.
- **Product**: variants with swatches, bundles, unit prices, quantity rules and volume pricing, subscriptions, a sticky add-to-cart bar, recommendations, recently viewed, reviews.
- **Orders and account**: order tracking and payments, a return or exchange request, profile, addresses, company, store credit.
- **Onboarding**: with `ONBOARDING=true`, three welcome pages over the home template's stock banners, shown once before the tabs. Debug builds can run it again from Account → Show onboarding.
- **Cart**: with `FREE_SHIPPING_THRESHOLD` set, a bar shows how much more the cart needs for free shipping. The app only shows the message: the free shipping rate itself is set in Shopify admin (Settings → Shipping and delivery), at the same amount. The cart also takes discount codes and shows the savings.

### Reviews (Judge.me)

Set `JUDGEME_PUBLIC_TOKEN` to the **public** token from Judge.me admin → Settings → Integrations → View API tokens. The product page then shows the rating summary and the reviews, and takes new ones. Never use the private token: anything in the config files ships inside the app.

Without a token the app reads the reviews through the endpoint Judge.me's own storefront widget uses. It shows the list and the count, but no star breakdown, and the average only when the rating metafield below is exposed or every review is loaded; a product with no reviews yet shows no reviews section. That endpoint is not a documented API and can change without notice, so set the token when you can. A store without Judge.me shows no reviews either way.

Rating stars on product cards come from the standard `reviews.rating` and `reviews.rating_count` product metafields, which Judge.me keeps up to date. They appear once those two definitions have **Storefront API access** on (Settings → Custom data → Products).

### B2B

When the signed-in customer is a contact of a company (Shopify B2B), the apps run every Storefront call as that company location: catalogue prices, quantity rules and volume pricing show on the product page, and checkout opens as the company. A contact with several locations switches between them on the Account screen.

### Returns and exchanges

The order page offers **Return or exchange items** when the store has self-serve returns on (Settings → Customer accounts) and something is returnable. Shopify's Customer Account API takes return requests only, so an exchange is sent as a return whose note names the wanted variant; complete it from the return in Shopify admin.

## Analytics

The apps can report to Google Analytics, Meta and MoEngage. Each is off until it is configured, and an app with none configured carries no analytics SDK.

| Provider | Configured by | Where it comes from |
|---|---|---|
| Google Analytics 4 | `android/app/google-services.json` and `ios/App/GoogleService-Info.plist` | Firebase console → Project settings → Your apps: add an Android app and an iOS app with this project's `BUNDLE_ID`, and download each one's file. The project needs Google Analytics turned on |
| Meta | `META_APP_ID`, `META_CLIENT_TOKEN` | Meta for Developers → the app: its app ID, and the client token under App settings → Advanced |
| MoEngage | `MOENGAGE_WORKSPACE_ID`, `MOENGAGE_DATA_CENTER` | MoEngage dashboard → Settings: the workspace ID. The data center is the number in the dashboard's address (`dashboard-03.moengage.com` is `3`) |

A Firebase file must be for this app's `BUNDLE_ID`: Google Analytics gets nothing from an app whose ID is not the one in its file.

- **Android** needs nothing more: the build adds an SDK when its file or its keys are there.
- **iOS with Xcode**: add the provider's Swift package to the App target (File → Add Package Dependencies). For Google Analytics also add `-ObjC` to the App target's Other Linker Flags (Build Settings): Firebase's package asks for it.
- **iOS with xtool**: `ios/Package.swift` already has the packages of the providers Argon was given. To add one later, add its package and its product there, next to Checkout Kit's. Firebase's file also goes in `ios/xtool.yml` (`- App/GoogleService-Info.plist`), and Meta's SDK reads three keys from `ios/Xtool-Info.plist`: `FacebookAppID`, `FacebookClientToken` and `FacebookDisplayName`.

| Provider | Swift package | Product |
|---|---|---|
| Google Analytics | `https://github.com/firebase/firebase-ios-sdk`, 13.0.1 or later | `FirebaseAnalytics` |
| Meta | `https://github.com/facebook/facebook-ios-sdk`, 18.1.1 or later | `FacebookCore` |
| MoEngage | `https://github.com/moengage/apple-sdk`, 11.3.0 or later | `MoEngage-iOS-SDK` |

Firebase 13 needs Xcode 26.2 or later (Swift 6.2.1 with xtool); with an older Xcode, use its 12.x releases.

### What is reported

Every screen and store reports to one hub, `Analytics`, and each provider plugs in behind it. The events, under Google Analytics' names: `screen_view`, `view_item_list`, `view_item`, `search`, `add_to_wishlist`, `add_to_cart`, `remove_from_cart`, `view_cart`, `begin_checkout`, `add_shipping_info`, `add_payment_info`, `purchase` and `login`. Meta gets its standard app events where it has one (product views, search, wishlist, cart, checkout, payment details, purchase), and MoEngage its own event names and the signed-in customer's id, email, phone and name. Product ids are Shopify's numeric ids, the ones Google's and Meta's catalogues use.

Debug builds print one line per event (`Analytics: add_to_cart {…}`) to logcat or the Xcode console. It is how to check the events without any provider account.

MoEngage push notifications and in-app messages are not included: they need FCM and APNs keys.

### Consent

The Account screen has a **Share usage data** switch under Privacy, on by default. While it is off, the apps report nothing. It is one switch: a store that sells in the EU needs a prompt before the first event, and the apps don't show iOS's tracking prompt (ATT), so Meta gets no advertising id on iOS.

### Purchases from a server (`server/`)

Argon writes this folder when Google Analytics or Meta is configured (or with `--server`). The keys that let a server report a sale, Google Analytics' API secrets and Meta's access token, must never be inside an app, so one small Cloudflare Worker holds them, and you deploy it to your own account.

Shopify tells the Worker about every new order, and it reports the ones placed in the app as a purchase, with the ids the app uses: Meta's event id is `purchase-<order id>`, and Google Analytics' `transaction_id` is the order's numeric id. It knows an app order by the attributes the app puts on a cart when it creates it (`_argon_platform`, and each provider's ids), which Shopify passes on as the order's additional details. They are put on once: a customer who switches "Share usage data" off after creating a cart is still reported for that cart.

Only the purchase goes through the server; every other event comes from the app alone. Who reports the purchase:

- **Meta: the app and the server, both.** Meta counts the two once, by the event id.
- **Google Analytics: one side only**, because it would count a purchase from each. `SERVER_PURCHASE` picks the side.
  - `false`, the default: the app reports the purchase itself, and the server sends Google Analytics nothing.
  - `true`: the app leaves the purchase to the server. Argon sets it when the project is generated with `--server`; to switch later, set it in both config files and release that version of the apps.

Turn `SERVER_PURCHASE` on only once the Worker is deployed with the Google Analytics secrets: from then on Google Analytics gets the apps' purchases through the Worker or not at all.

`server/README.md` has the deploy steps and where each secret is found.

## Demo store (`mock.shop`)

`mock.shop` has no metaobjects, so Home shows the template's stock banners over the store's collections. It has no customer accounts or reviews app either: the Account tab offers **Preview with a sample account** (sample orders, a return, a company) and product pages show sample reviews, so those pages can be seen. It also doesn't implement `nodes(ids:)`, so the Wishlist tab and Recently viewed stay empty there. They work on real stores. The demo sets `FREE_SHIPPING_THRESHOLD=150` so its cart shows the free-shipping bar.

## Edit the home screen

In Shopify admin go to **Content → Metaobjects → Mobile screen → Home**. The home screen is an ordered list of sections: *Mobile banner*, *Mobile products* and *Mobile collections* entries. Add, reorder or edit them and save; the apps pick it up with no release. If the entry is missing or empty, the apps show a fallback home built from the store's brand, collections and products.

## Store prerequisites

- **New customer accounts** are on (Settings → Customer accounts), or login won't work.
- The **storefront password is off** (Online Store → Preferences), or Checkout Kit can't open checkout.
- **Products and collections are available to the Headless storefront's sales channel**, and its Storefront API keeps the metaobject read permission, or the app shows an empty or fallback home.
- **Collection and search filters** appear only after the Search & Discovery app has filters configured.
- **Storefront API permissions** (Headless channel → Storefront API): the apps leave out what a permission you turn off would have fed. Without `unauthenticated_read_product_inventory`, for example, the product page shows no "Only 3 left".

## Publishing

- Ship each client's app from **the client's own** Apple Developer and Google Play Console accounts (Apple guideline 4.2.6: an app built from a template or generator must be submitted by the owner of its content). Add the agency as a team member.
- Both stores require an in-app way to start **account deletion**. The Account screen's *Delete account* opens `https://<SHOP_DOMAIN>/pages/contact`; make sure that page exists on the store and that someone handles the requests.

## Troubleshooting

If Argon stopped while creating the home screen content, it can leave some entries behind. Delete the *Mobile banner*, *Mobile collections*, *Mobile products* and *Mobile screen* entries it created (Content → Metaobjects) before running it again; otherwise the re-run fails on the taken handles.
